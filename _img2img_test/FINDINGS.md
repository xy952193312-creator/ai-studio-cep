# 图生图可行性实测报告

**日期**：2026-10-20
**服务**：一个 OpenAI 兼容协议的中转服务（文中做了脱敏，不写具体地址）
**模型**：gpt-image-2
**目的**：确认 `POST /v1/images/generations` 的 `image` 字段是否真的生效，以此决定「AI 生图页加图生图」是否值得做。

## 结论（先说答案）

**`/v1/images/generations` 会忽略 `image`，但 `/v1/images/edits` 完全可用。** 四轮对照实验证明生成端点不认 `image`；随后探测到官方图生图端点 `edits` 在这家中转站是通的，且效果正确（详情见下方「转折」一节）。

所以图生图**可以做，但不能在 `generations` 上做**——必须按 OpenAI 官方架构，有图时切到 `edits`（multipart）。如果直接往 `generations` 塞 image，会得到一个和 `quality` 一样的空转功能。

## 方法

所有测试都用对照实验（同一提示词，唯一变量 = 是否带 `image`），避免"看起来像"的主观判断。
key 从已运行面板内存借用，不落盘。

### 轮次 1：白猫 + 红蓝图（探索性）

- 提示词：`一只白色的猫坐在木窗台上，柔和日光`
- 参考图：512² 上半纯红 / 下半纯蓝 / 正中大黄圆（特征极强）

结果：两组都是白猫，参考图颜色零出现。

**发现的疑点**：无图组 1024²，带图组 1254²。尺寸不一致曾被误读成"服务端收到了 image"，但轮次 3/4 排除了——无图组同样出现 1254²，尺寸只是模型的不确定性。

### 轮次 2：抽象画（失败设计）

- 提示词**自己说了颜色**：`上半部分是鲜红色，下半部分是深蓝色，正中央一个亮黄色圆形`

三组（无图 1024 / 带图 1024 / 无图 1254）产出几乎一致。

**这轮实验作废**：提示词把答案说出来了，纯文生图也能画出红蓝黄，无法区分 image 是否生效。

### 轮次 3：决定性测试

- 提示词**完全不提颜色**：`一张极简抽象几何海报，纯色平涂，无渐变无纹理`
- 参考图：上红 / 下蓝 / 中心黄

| 组别 | 尺寸 | 位置一致性 | 结构匹配 |
|---|---|---|---|
| A 无图 | 1024² | 33% | 有红、黄圆、黑块，构图与参考图无关 |
| B 带图 | 1254² | **0%** | 同样是包豪斯色块，只是色块位置左右镜像 |

两张图构图高度相似（圆形 + 对角线 + 三色），但**没有任何一组复现"上红下蓝中心黄"**。B 组把红色换到了右侧、黄色换到左上——如果 image 是 init_image，这种位移不可能发生。

### 轮次 4：排除性验证（最关键）

前几轮还留一个口子：也许服务端把 image 当"风格参考"用，结构上不强绑，所以肉眼看不出。

- 参考图换成 **512² 纯灰噪点图**（无任何语义）
- 提示词：`一张极简抽象几何海报，纯色平涂，色彩鲜明，高质量设计作品`

| 指标 | A 无图 | B 带噪音图 | 判定 |
|---|---|---|---|
| 低饱和(灰)像素占比 | 42.2% | 32.6% | 带图反而**更鲜艳**（-9.6pt） |
| 平均饱和度 | 49.5% | 50.6% | 几乎一致 |
| 颗粒度 | 81.5 | 88.3 | 在波动范围内 |
| 色彩种类 | 210 | 262 | 无退化 |

真图生图用噪点做底，出图必然被拖成灰糊；实际产出是**干净锐利的色块海报，甚至比无图组更鲜艳**。噪点图对结果零影响。

**这一轮彻底封口：image 不参与生成。**

## 根因

中转站的 `/v1/images/generations` 是对 OpenAI Images API 的简单代理。OpenAI 官方**没有**在 `images/generations` 上提供 init_image / 参考图能力——图生图/改图走的是另一个端点 `POST /v1/images/edits`（multipart/form-data）。中转站把多余的 `image` 字段静默丢弃，返回 200，所以任务照跑、也不报错。

这和 `quality` 的遭遇完全同构：**字段能发、服务不校验、也不生效**。

## 转折：`/v1/images/edits` 是通的

既然生成端点不收 image，就去试官方放图生图的那个端点。**结论：完全可用，而且效果正确。**

### 探测过程

| 步骤 | 结果 | 说明 |
|---|---|---|
| `POST /v1/images/edits` 无鉴权 | `401 Token not provided` | 端点存在（不是 404） |
| 带 key + multipart（Node 手搓 boundary） | `200`，返回直链 | **成功** |
| 同上，响应里的 usage | `image_tokens: 415` | **参考图真的被计费、被读取了** |
| 面板内 `fetch + FormData`（浏览器自动 boundary） | `200`，返回 `task_xxx` | 工程里能直接用，且**支持 `async:true`** |
| 用 `GET /v1/images/generations/task_xxx` 轮询该任务 | `200 in_progress` | **现有轮询链路可直接复用** |

### 效果验证（决定性）

- 参考图：上红 / 下蓝 / 中心黄圆
- 提示词：`把这张图改成一张水彩风格的风景画`
- 产出（`edit-out.png`）：**红色天空 + 蓝色海面 + 正中黄色落日**，完全继承了参考图的三段式布局，只把质感换成水彩

对比前面四轮：`generations` 无论带不带图，产出的都是提示词描述的东西；`edits` 的产出是参考图的**改造版**。这就是真图生图。

## 对产品的影响

架构照 OpenAI 官方来即可，UI 不需要妥协：

```
无图  -> POST /v1/images/generations  (JSON)
有图  -> POST /v1/images/edits        (multipart/form-data)
```

- 两者都支持 `async: true`，返回同形 task id；
- 轮询统一走 `GET /v1/images/generations/{id}`，**不用为 edits 单独写一套**；
- 之前怀疑的"multipart 在 CEP 里发不出去"已被面板内实测排除；
- 隐忧：`edits` 未验证 `quality` / `n>1` / 各模型的兼容性，接入时对这些字段要保守（缺失就不发）。

## 补充实测：多图到底认几张（2026-10-20 晚）

「上限 10 张」这个功能能不能做，取决于服务端吃几张图。实测结论：**全读、全计费、会融合**。

### 实验设计

参考图统一 512×512、纯色底 + 中心白圆（特征强且不退化），三组特征色分开测：

| 阶段 | 内容 | 目的 |
|---|---|---|
| Stage 0 | 2 张，打印完整响应 | 找 `image_tokens` 藏在哪一层 |
| Stage 1 | 1 张绿 / 1 张橙 / 3 张 / `image[]` 变体 | 计费量是否随张数线性增长 |
| Stage 2 | `[绿,橙]` vs `[橙,绿]` | 顺序是否影响结果 |
| Stage 3 | 红/黄/蓝三张，提示词要求三色都出现 | 排除「只认第一张」的最后可能 |

提示词一律用 `把这张图改成水彩风格的抽象画，保留画面的主要颜色和构图`——**不写"风景画"**，因为风景天然偏绿会污染主色判定（第一版就踩了这个坑，`multi-probe.png` 74% 绿其实是"水彩风景都偏绿"，不是"只读了绿图"）。

### 计费量：严格线性，全部计费

`usage.prompt_tokens_details.image_tokens`（512² 单张基准 415）：

| 输入 | image_tokens | 倍数 |
|---|---|---|
| 1 张 | 415 | 1.00× |
| 2 张 | 830 | 2.00× |
| 3 张 | 1245 | 3.00× |

**服务端把每一张都读进去并计费了**，不存在"只收第一张、其余静默丢弃"。

### 视觉结果：真的融合

| 输入 | 输出主色 | 看图 |
|---|---|---|
| 绿 单张 | 绿 82.5% | 纯绿水彩 |
| 橙 单张 | 橙 87.6% | 纯橙水彩 |
| **[绿, 橙]** | 绿 22.9% / 橙 23.3% | **左绿右橙并排双色块水彩** |
| [橙, 绿] | 橙 80.2% | 只有橙 |
| 3 张(绿橙紫) | 绿 80.4% | 只有绿 |
| **[红, 黄, 蓝]** | 红 43.9% / 蓝 4.6% / 绿 1.3% | **红黄蓝三色水彩融为一体** |

最后一组是决定性的：三张参考图的三种颜色全部出现在同一张输出里，构图还保留了"中心白圆"。**多图融合成立。**

### 一个重要的坑：不要用"顺序互换"来判定

`[绿,橙]` 融合了、`[橙,绿]` 只出橙——乍看像"只认第一张"，实际是**模型的语义选择**：绿和橙同属暖色、色相接近，能合成"双色块"；而把暖橙改成冷绿，模型认为违背"改造成水彩"的意图，就只保留了橙。

所以判定多图是否生效，**必须用色相分离度大的组合（红/黄/蓝），并且提示词明确要求"多种颜色都要出现"**。用相近色 + 顺序对照会得出完全错误的结论。

### 第一张 = 底图/主图，其余 = 参考图

用户明确：**第一张肯定作为主图或者底图来使用**。实测数据支持这个语义：

- `[绿,橙]` 的融合结果是**左绿右橙** —— 第一张占据主位（左侧），不是随机排布；
- `[橙,绿]` 发生语义冲突时，保留的是**第一张橙** —— 第一张有优先权。

所以 `images[]` 的顺序不是无关紧要的数组，而是**有主次的序列**：

```
images[0]  底图/主图  —— 决定画面的基底，语义冲突时胜出
images[1..] 参考图     —— 参与融合，权重低于底图
```

由此推出两条硬要求：

1. **UI 顺序必须原样传下去** —— 缩略图怎么排，`buildEditsForm` 就怎么 append，中间不能有任何排序/去重/过滤；
2. **拖拽排序是真功能，不是装饰** —— 用户靠拖动来决定"哪张当底图"，所以第 1 位的角标要显示成「底图」，其余显示「参考 N」，且换位后角标要**原子重算**（不能出现两个「底图」或角标错位）。

### 对实现的要求

1. 上限可以直接放开到 10，服务端不会拒绝，也不会漏计费（用户看得见浪费）。
2. `image`（重复同名）和 `image[]` 两种字段都被接受，**现有 `buildEditsForm` 发的重复 `image` 是对的**，不用改。
3. 融合靠模型语义，不保证每张都体现——这是模型行为，不是 API 契约，**界面不要加任何提示文案**（用户已明确要求）。
4. 张数越多越慢越贵：实测 1 张约 40s、3 张约 45s，计费按张线性叠加。这是用户自己的选择，不做拦阻。

## 补充实测：上限到底是几张（2026-10-20 夜，`wide` 阶段）

**动机**：`MAX_IMAGES` 从 3 直接放到 10 是拍脑袋的，没有数据。而 `image_tokens`
严格线性（每张都扣钱），万一第 4 张起不进画面，就是白扣钱。

**方法**（`node tools/_test_multiimg.js wide`，或指定档位 `wide 9`）：
10 种高分离色（红/黄/蓝/绿/橙/紫/青/洋红/黄绿/粉，统一 512×512），
按 3 / 6 / 10 张递增提交，提示词统一要求「每张图各自的颜色都要出现」。
判据两条硬指标：`image_tokens` 是否继续线性 + **12 格色相直方图里的颜色种类数**（占比 ≥3% 的格子数）。

**结果**：

| 张数 | image_tokens | 色相分布（≥1%） | 颜色种类 |
|---|---|---|---|
| 3（红黄蓝） | 1245 = 415×3 | 0°:24.4 30°:28.8 60°:1.1 210°:37.5 330°:5.5 | **4** |
| 6（+绿橙紫） | 2490 = 415×6 | 0°:17.5 30°:27.6 60°:1.1 90°:7.1 120°:8.6 180°:2.4 210°:14.1 270°:12.3 300°:1.3 330°:7.3 | **7** |
| 10 | — | **HTTP 400** `{"code":"invalid_reference","message":"参考图最多 9 张，请减少后重试。"}` | 失败 |

**结论**：

1. **多图是真功能，不是只有第一张生效。** 3 张出 4 种颜色 → 6 张出 7 种，
   新增的绿（120°）、紫（270°）、橙（30°）都实打实进了画面。
2. **上限是 9，不是 10。** 第 10 张不是被静默忽略，是**整单 400 拒绝**——
   用户选满 10 张点生成，拿到的是一次失败，不是「少用一张」。
   `MAX_IMAGES` 已改为 9（generate.js / edit.js 两页必须一致）。
3. `image_tokens` 线性到第 6 张仍成立（2490 = 415×6），所以 9 张 ≈ 3735，每张都计费。

**补跑 9 张（`node tools/_test_multiimg.js wide 9`）确认上限可用**：
HTTP 200，`image_tokens = 3735 = 415×9`，色相分布 12 格里 **10 格 ≥3%**：
0°:17.8 30°:19.5 60°:8.7 90°:5.1 120°:4.6 150°:3.2 180°:11.0 210°:9.0 240°:2.0
270°:8.5 300°:8.3 330°:2.3 —— 9 种输入色**全部**进了画面。

所以 9 是「能用满」的档位，10 是「整单失败」的档位，二者不能混为一谈。

**产出**：`multi-wide-3.png` / `multi-wide-6.png` / `multi-wide-9.png` / `wide-*.png`（10 张底图）。

**复现**：`node tools/_test_multiimg.js wide`（3/6/10）或 `node tools/_test_multiimg.js wide 9`
